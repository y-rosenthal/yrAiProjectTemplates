9 Question Collections — SPEC 0.0.2

This spec defines question collections: named sets of questions that can be used as a test, a homework assignment, or a study list. It extends the MVP (SPEC-0.0.1) by adding UI and persistence for creating and managing collections, and clarifies terminology so that “test” is reserved for the activity of taking and submitting answers, not for the underlying set of questions.

References: SPEC-0.0.1.qmd, PRD-0.0.1-v003.qmd, QUESTION-FORMAT-0.0.1.qmd, QUESTION-MODULE-SPEC.qmd.
See DOC-GUIDE-v001.qmd for document versioning.

9.1 Purpose and scope

9.1.1 What is a question collection?

A question collection (or collection) is a named, ordered list of question identifiers. The same collection can be used in different ways:

  • As a test — A learner takes the collection under timed/untimed conditions, submits answers, and receives a score. This is the current “take a test” flow.
  • As homework — The same set of questions might be assigned as homework (same or different submission rules in a future version).
  • As a study list — A topic-focused set of questions for practice, with or without grading.

The system does not assume every collection is a “test.” Naming and UI should reflect that collections are generic question sets; the use of a collection (e.g. “Take as test”) is a separate action.

9.1.2 Naming: “Collection” vs “Test”

Term Meaning in this spec
Question collection A named set of questions (data). Can be used as a test, homework, or study list.
Test The activity of taking a collection: start session, answer questions, submit, get score. “Test” = one usage of a collection.
Test session One user attempt (e.g. one “take” of a collection). Already in DB as test_sessions.

So: collections are the reusable question sets; tests (and test sessions) are the act of taking and submitting. The UI and docs should avoid implying that every collection is “a test”; prefer “collection” for the entity and “Take as test” (or similar) for the action.

9.1.3 Scope for 0.0.2

  • In scope
    • Persist question collections in the database (new table and APIs).
    • UI to create a new collection: choose a name (and optional description) and select which questions to include (from available questions).
    • UI to list collections; from the list, the user can take a collection as a test (existing take flow) or later edit/delete (optional for 0.0.2).
    • Replace or refactor the current config-based “tests” (tests-config.ts, TESTS_CONFIG env) so that collections are the source of truth; “take test” uses a collection id.
    • Update documentation and code naming so that “collection” is used for the set of questions and “test” is used for the taking/submission flow where appropriate.
  • Out of scope for 0.0.2
    • Editing or deleting collections (can be added later).
    • Different “modes” per collection (e.g. homework vs test); for now, every collection can be “taken as a test.”
    • Ordering of questions within a collection (fixed order or shuffle) is MVP-defined; spec allows storing order.

9.2 Data model

9.2.1 New table: question_collections

Store one row per collection.

Column Type Description
id uuid, PK Unique collection id (e.g. gen_random_uuid()).
title text, not null User-facing name (e.g. “Bash basics”, “Week 3 homework”).
description text, nullable Optional description.
owner_id uuid, nullable, FK → auth.users User who created the collection. Nullable to allow system/seed data.
created_at timestamptz When the collection was created.

9.2.2 New table: question_collection_items

Store the questions in each collection with explicit order.

Column Type Description
id uuid, PK Unique row id.
collection_id uuid, not null, FK → question_collections(id) ON DELETE CASCADE Which collection.
question_logical_id text, not null Question logical id (same as in question_versions / storage).
position int, not null 1-based order within the collection.

Unique constraint on (collection_id, position) or (collection_id, question_logical_id) depending on whether the same question can appear more than once; for 0.0.2, one question per collection is sufficient, so unique on (collection_id, question_logical_id) is acceptable. Order is given by position.

9.2.3 Relationship to existing tables

  • test_sessions: Keep test_id but treat it as collection_id (uuid). So “test_id” in test_sessions is semantically “the collection id used for this test.” Migrations can rename the column to collection_id for clarity, or keep the name and document that it refers to a collection; either way, the value is the uuid from question_collections.id.
  • answers: No change; they reference session_id and store question_id / question_version.

9.2.4 RLS (row-level security)

  • question_collections: Authenticated users can read all collections (so everyone can “take” any collection). Insert: authenticated users can create (set owner_id = self). Update/delete: only owner (or later, admin) if you add edit/delete in 0.0.2.
  • question_collection_items: Same as collections: read for authenticated; insert/update/delete only when the user owns the parent collection (or via policy that checks question_collections.owner_id).

9.3 API

9.3.1 Collections

Method / path Auth Purpose
GET /api/collections Authenticated List all collections (id, title, description, question count). Optional: filter by owner.
GET /api/collections/[id] Authenticated Get one collection by id with ordered list of question logical ids (for “take as test” flow).
POST /api/collections Authenticated Create collection. Body: { title: string, description?: string, questionLogicalIds: string[] }. Returns { id, title, ... }.

For 0.0.2, no PATCH/DELETE is required; they can be added in a later spec.

9.3.2 Backward compatibility with “take test” flow

  • Start test: POST /api/tests/[id]/start — id is now a collection id (uuid). Server loads collection by id, gets ordered question_logical_id list, creates a test_session with test_id = collection_id (or renames to collection_id), returns sessionId, questionIds, etc. Same contract as today.
  • Submit test: POST /api/tests/[id]/submit — unchanged; id is still the collection id used for this test.
  • List “tests” for the learner: GET /api/tests can be replaced by GET /api/collections (or both supported, with /api/tests returning collections so the take-test UI keeps working). Prefer a single source: list collections, and the “Take as test” action uses the collection id.

So: the existing take-test API paths can remain under /api/tests/ for backward compatibility, but they operate on collection ids; the tests list page should be driven by collections.

9.4 UI

9.4.1 Home / navigation

  • Collections (or “Question collections”): Link to list of collections. Replace or supplement the current “Take a test” link so that the primary entry is “Collections” and from there the user can “Take as test” for a given collection.
  • Create collection: From the collections list, a button/link “Create collection” that goes to the create-collection page.

9.4.2 Collections list page

  • Route: e.g. /collections (or keep /tests and repurpose as “Collections you can take”).
  • Content: List all collections (title, description, question count). Each row has an action “Take as test” that goes to the existing take flow (e.g. /tests/[id]/take where id is the collection uuid). Optional: “Create collection” button.

9.4.3 Create collection page

  • Route: e.g. /collections/new.
  • Content:
    • Title (required): text input.
    • Description (optional): textarea.
    • Questions: Multi-select or checkbox list of available questions. Questions are loaded from GET /api/questions or GET /api/questions/my (or a dedicated “list all questions for picker” endpoint). User selects which questions to include; order can be list order or a separate ordering step (0.0.2: order = order in the list when submitted).
    • Submit: POST to POST /api/collections with title, description, questionLogicalIds; then redirect to collections list or to the new collection’s “Take as test” page.

No edit/delete UI required for 0.0.2.

9.4.4 Take flow (unchanged conceptually)

  • Route: /tests/[id]/take — id = collection id.
  • Behavior: Same as today: start session, load questions by logical id (from collection), answer, submit. Only the source of questionIds changes (from config to DB collection).

9.4.5 Naming in the UI

  • Prefer “Collections” for the list and “Create collection” for the creation flow.
  • Use “Take as test” (or “Take test”) for the action that starts a test session from a collection, so it is clear that the collection is the content and “test” is the activity.

9.5 Code and config changes

9.5.1 New and moved code

  • Migrations: New migration adding question_collections and question_collection_items, and RLS. Optionally rename test_sessions.test_id → collection_id and update API to use collection id everywhere.
  • Config: src/lib/tests-config.ts (or equivalent) should not define a static list of tests for production. Instead:
    • Option A: Remove env-based tests config; all “tests” come from DB collections. Seed one default collection if needed for development.
    • Option B: Keep a fallback: if no collections in DB, read from env/config for backward compatibility; otherwise use DB.
  • API routes: Add src/app/api/collections/route.ts (GET list, POST create) and src/app/api/collections/[id]/route.ts (GET one with question ids). Update src/app/api/tests/[id]/start/route.ts (and optionally submit) to resolve “test” id as collection id and load question ids from question_collection_items.
  • Lib: e.g. src/lib/collections.ts or src/lib/collections-db.ts for helpers that load collections and items from the DB.

9.5.2 Naming and documentation

  • Code: Prefer collection and collectionId where the entity is the set of questions; keep test for session/attempt (e.g. test_sessions, “start test”, “submit test”). Types: Collection, CollectionItem; avoid TestDef for the collection itself—rename to Collection or keep TestDef only if it is used purely for the “take test” payload (then document that it is backed by a collection).
  • Docs: Update SPEC-0.0.1 (or add a short note) that “tests” in the student sense are backed by question collections. Update DEVELOPER-GUIDE, README, and any doc that says “create tests” to say “create collections” and “take a collection as a test.” Update QUESTION-MODULE-SPEC section “Tests and test flow” to say that tests are taken from collections and that collection ids are used as test ids in the session.

9.6 Summary of terminology (for implementation and docs)

Concept Use in UI/code/docs
The set of questions Collection (question collection)
Creating a set of questions Create collection; user chooses questions to add
The activity of answering and submitting Take (as) test; test session
DB table for the set question_collections + question_collection_items
DB table for the attempt test_sessions (unchanged); test_id = collection id

This keeps the codebase and docs clear: collections are the reusable question sets (tests, homework, study); tests are the timed/untimed take-and-submit experience backed by a collection.
